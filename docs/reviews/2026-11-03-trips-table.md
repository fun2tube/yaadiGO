# Phase 1d, trips into a real table: DevOps + PM + CTO review

**Date:** 2026-11-03 · **Spec:** docs/design/ai-cofounder.md §6a

## CTO: what was built

**`trips` table (migration 0009):**

- One row per trip, group or customized.
- The itinerary is one jsonb validated by `TripContentSchema`: `live`, plus
  `draft` while edits are pending.
- Lifecycle columns: status, version, source, redirect, published and
  archived stamps.
- **Generated by Postgres from `live`:** title, destination, region, theme,
  nights (parsed from "6N / 7D") and price from. Queryable and indexed,
  and they can never disagree with the content.
- CHECKs:
  - kind is group or customized;
  - status is one of the four;
  - version ≥ 0;
  - **a published or internal trip must have live content.**

**`trip_versions`:** one immutable snapshot per publish, unique
`slug@version`.

**The move from `documents`:** the same migration moves trips and versions
saved by the admin into the new tables, then deletes the documents.

**The move from code** (`lib/cms/trip-import.js`):

- Each record is built from what visitors see now (code plus any old
  override), through the editor's own converter.
- It runs after every deploy via `/api/cron/maintenance` (CRON_SECRET, called
  from inside the container by `setup-vps.sh`). It does nothing once done,
  and a unique slug stops a double import.

**Repository:** the record store now writes `createdAt`/`updatedAt` as dates
and skips generated columns.

**Unchanged:** departures and seats (still the booking code's), and every
screen and API that used `lib/cms/trips.js`.

## DevOps: verified

- **`lib/trip-model.parity.test.js` (34 tests):** every coded trip
  round-trips code → content → page shape. It first failed for four trips
  (F1).
- **`src/db/trips-table.test.ts` (4 tests, real Postgres):**
  - the documents move runs on hand-made rows and leaves other collections
    alone;
  - a trip goes from draft to published (version 1), gets the generated
    columns (nights 4, ₹38,500 stored as 3850000 paise), keeps live unchanged
    by a draft edit, republishes as version 2, and archives with a redirect;
  - Postgres refuses a published trip with no content;
  - importing the coded trips twice moves them once; afterwards every shown
    field of every trip matches what was shown before.
- **Rendered pages, local store:** all 37 pages (home, both listings, 34
  trips) captured before the import, the import run twice (33 moved, then 0;
  the 34th was already managed), and captured again.
  - The first comparison found F2 on 13 pages.
  - After the fix: **36 of 37 identical**. The one difference is that fix
    showing on the trip edited earlier.
  - Unauthorised calls get 401.
- **Full suite:** 532/533. The one failure is the known `trip-seats` date
  test (#183).

## Findings

**F1 (S2): four group tours could not be opened in the trip editor. Fixed.**
Himachal Monsoon, Vietnam, Bali and Thailand each have a "land only"
joining point priced as a saving (−₹28,000 and so on). The schema allowed
only additions, so `contentFromTour` threw. That trip's editor failed today,
and the move would have failed too. Joining points now accept a saving (the
editor says how); room sharing still only adds.

**F2 (S2): on every trip edited in the admin, the itinerary showed with
every day closed. Fixed.** `ItineraryDay` opened `day.day === 1`, a number.
Content stores days as text ("1", so "1–2" is possible), so no managed trip
ever opened its first day. That has been true since phase 1. The move would
have spread it to all 14 group tours. Found only by comparing rendered pages.
The unit tests treated "1" and 1 as equal, which is the reason both kinds of
check exist. The first day now opens by position.

**F3 (S2): the record store could not write a whole record back to a real
table. Fixed.** `mutateBy` handed Drizzle `createdAt` as a string. It was
latent because only document collections used `mutateBy`; trips would have
failed on every publish.

**F4 (S3): there is no destinations entity yet.** In the code,
"destinations" means customized trips. Places (Kashmir, Spiti) exist only as
text on trips and hotels. A real `destinations` table, with place pages and
SEO, is the next step. → #203.

**F5 (S3): the code catalogue is still the fallback.** `lib/tours.js` and
`lib/packages.js` still render a trip that has no record: first boot, local
development without a database. Retire them once the live import has run and
held for a while. → #204.

**F6 (S4): group departures still come from code plus `tripOverrides`
documents.** They are not on the `departures` table yet. The inventory move
is its own piece of work, as before. → #205.
